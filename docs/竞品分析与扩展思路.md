# 蛋白钱包 · 竞品分析与扩展思路

2026-11-03。按「夯级背锅大王」那篇「产品面试向 Vibe Coding 选题思路」的框架复盘：先从真实痛点出发定用户标签 → 再判断生态位（蓝海证需求、红海证细分更专业）→ 差异化走加法（补未闭环流程）或减法（缩小人群/场景）。

## 1. 蛋白钱包在这个框架里的位置

- **痛点来源**：自己和健身圈同学。符合帖子「从生活里真实的问题出发，你自己就是核心用户」。
- **用户标签**：生活费有限、想增肌、靠食堂/连锁/外卖解决三餐的在校大学生。已经比「需要记饮食的人」小得多，够用。
- **生态位：红海**。饮食记录是成熟市场（MyFitnessPal、薄荷、Cal AI 一堆），市场已经验证了「记饮食」这个需求。按帖子的说法，红海要证明的是：在细分场景里的方案更专业、更完整。
- **差异化同时用了减法和加法**：
  - 减法：只追 2 个数（蛋白质、钱），只服务 1 类人（增肌大学生），只覆盖 3 个场景（食堂 / 连锁 / 外卖 + 自炊）。
  - 加法：补上「钱」这条没人闭环的线。一张小票同时记账 + 记餐，产出 ¢/g 蛋白质单价。营养 App 不管钱、记账 App 不管营养，这条缝隙是产品的立足点。
- **「专业」体现在数据层，不在模型**：连锁官方营养表（5 家逐行核实）+ 芝大食堂 640 道菜官方库 + 自建评测集和命中率指标。模型只负责「认出是哪道、几份」，算术由代码做。这是回答「你不就是套了个 API 吗」的核心。

## 2. 竞品分三类

| 类别 | 代表 | 它们擅长 | 它们不做 / 做不了 | 蛋白钱包的差异 |
| --- | --- | --- | --- | --- |
| 通用 AI | 豆包、DeepSeek、ChatGPT | 单次拍照问「这盘多少蛋白」，回答快、免费、不用装新 App | 持久化和跨周聚合；锚定官方数据；输出不确定性；钱 | 工作流 + 数据资产 + 评测，不是单次问答 |
| 垂类饮食记录 | MyFitnessPal（Meal Scan 付费 $79.99/年）、薄荷健康（小麦 AI）、Cal AI、轻断食类小程序 | 大食物库、条码、微量营养素、减脂人群全覆盖 | 钱；增肌视角；诚实区间（第三方实测拍照估算每餐偏差约 345 kcal） | 减法到增肌大学生 + 加法补钱 |
| 校园食堂 App | DineND、dEat、MacroPeak、UPlate、DormDish AI、Bruin Eats、DavisDine | 从食堂菜单出发，看宏量、按目标规划一餐 | 食堂以外的场景（连锁、外卖、自炊）；记录「实际吃了什么」；钱；大多单校、iOS-only | 消费账本 vs 菜单浏览器；跨场景 ¢/g 比较 |
| 记账 App | 随手记、鲨鱼记账 | 记钱 | 营养 | 一次动作两件事 |

### 2.1 对通用 AI 的回答（面试版）

豆包能告诉你「这盘大概 40 g 蛋白」，但做不到三件事：

1. **持久化和聚合**：今天差多少、本周 ¢/g 最高的是哪一餐、蛋白达标几天。聊天窗口里的数字过了就没了。
2. **锚定官方数据**：通用模型对 Chipotle 鸡肉碗是裸猜；蛋白钱包先匹配官方表，模型只判断配料组合，所以能报出可测的区间命中率。通用 AI 没有「命中率」这个概念，因为它没有评测集。
3. **诚实的不确定性**：聊天里模型倾向给一个自信的单点值。蛋白钱包强制输出区间 + 置信度 + 依据，界面上实线 / 虚线区分。

帖子里的切换成本问题也要正面回答：用户为什么不继续用豆包？因为拍一张小票同时记账 + 记餐，比在聊天里打字描述再自己记到别处更省事，切换成本是负的。但要诚实：通用 AI 的记忆和工作流能力在增强，这个差距要靠数据层（连锁表、食堂库、评测集）维持，靠 UI 维持不住。

### 2.2 对垂类记录软件的回答

- 它们面向所有减脂人群，功能布局重（微量营养素、食谱、社区），录入靠搜索 + 克数，对吃食堂的人摩擦极高。
- 它们以卡路里为中心，假精确（单一数值），而独立实测显示拍照估算误差很大。蛋白钱包反向设计，把「不确定」做成界面语言。
- 它们都不管钱。对生活费有限的学生，「这顿值不值」比「这顿多少卡」更接近真实决策。
- MyFitnessPal 的拍照功能在付费墙后，大学生付费意愿低。

### 2.3 对校园食堂 App 的回答（这是新发现，直接影响 feed 想法）

搜索发现「食堂菜单 + 蛋白质 + 按目标规划」已经是一个小红海：DineND（圣母）、Bruin Eats（UCLA）、DavisDine、UPlate、MacroPeak、DormDish AI 等，几乎每所大学都有学生做了一个。这说明两件事：

1. 「食堂 + 蛋白」的需求是真的，不用再证明。
2. 如果蛋白钱包把重心转向「食堂 feed」，就是在和这些 App 正面竞争，而且失去了自己的差异（钱、跨场景、小票）。

它们是「菜单浏览器」，从菜单出发帮你规划；蛋白钱包是「消费账本」，从你实际吃了什么、花了什么出发。feed 只能是账本的一个加法，不能变成产品本身。

## 3. 「结合食堂菜谱做每日推荐 feed」要不要做

**结论：做，但做成「差额 → 今天去哪补」的官方数据排序，不做「AI 推荐」。**

为什么做（帖子的加法定义）：加法是补上尚未闭环的流程。现在首页停在「今天蛋白还差 35 g，预算还剩 $9」，用户的下一个问题一定是「那我去哪吃」。这一步没闭环。

三个约束，决定它长什么样：

1. **数据约束**：现在只有 640 道菜的菜品库，没有每日菜单。Dine On Campus 的 API 在 Cloudflare 后面，每日菜单列表要网站自己的请求签名，我们不绕。可行路径：
   - 用户拍食堂菜单板 / 截图 → 和菜品库匹配，复用现有的拍照管线。这和产品的「拍一张」交互一致。
   - 种子期由自己每周手动快照一次当周菜单（5 到 8 个种子用户够用）。
   - 退一步：不做每日，做「每个食堂的常驻高蛋白榜」（静态，从菜品库算），也有价值。
2. **定价约束**：食堂刷卡是固定价，一餐内所有菜 ¢/g 都退化成 0。食堂内的指标要换成「一刷蛋白上限」（一次 swipe 最多能拿多少蛋白）。跨场景比较（食堂一刷 vs Chipotle $11.5）¢/g 仍然成立，而且正是其他食堂 App 没有的视角。
3. **伦理约束（PRD Non-goal）**：「不推荐你该吃什么」是因为营养建议有专业责任、模型幻觉风险。排序官方数据不碰这两条：零模型生成，纯代码对官方每份蛋白排序，再用今日差额过滤。文案用「今天菜单里蛋白最高的三道」而不是「你应该吃」。PRD 里 Non-goal 那一行改写成「不生成饮食建议，只对官方数据排序」，原理由不变。

**先验证再做**（帖子的核心要求）：

- 问种子用户：「看到差额数字之后，你下一步做什么？」如果答案是「打开食堂菜单看有什么」，就做。
- 小红书 / Reddit r/uchicago 搜「dining hall protein」「食堂 蛋白质」，看抱怨和点赞量。
- 看上面那些校园 App 的低分评论，常见抱怨大概率是「菜单不准」「没有我学校」「要钱」，这些就是它们的缺陷，也是我们的切入点。

## 4. 其他可以做深的方向（按优先级）

1. **先把 30 张评测集拍完**。帖子说 AI 不能证明需求真实，数字才能。命中率、区间宽度、小票解析准确率三个数是简历和面试的硬通货，比任何新功能都值钱。
2. **份量校准**：×0.5 / 1 / 1.5 / 2 按钮已上线，看修正率是否下降，这是「用户数据反哺设计」的故事。
3. **餐卡经济学**：meal plan 是固定成本，可以算「每刷有效蛋白」「本周没用的 swipe 浪费了 $X」。这是钱的视角延伸，所有竞品都没有。
4. **国内校园版**：货币已解耦，但国内食堂没有公开营养数据，是最大难点。先不做。
5. **保持减法**：社交、微量营养素、食谱继续不做。

## 5. 简历 / 面试三句话

- 市场定位：饮食记录是红海，切入点是「营养 App 不管钱、记账 App 不管营养」的缝隙，用减法（增肌大学生）+ 加法（¢/g）做差异。
- 和通用 AI 的区别：通用 AI 做单次估算，蛋白钱包做工作流 + 官方数据锚定 + 可测的命中率，输出区间而不是单点。
- 和食堂 App 的区别：它们是菜单浏览器，我们是消费账本；feed 作为「差额→去哪补」的加法接在账本后面，只排序官方数据，不生成建议。
